**七项未解决问题及修改方向**

**1. 顶部两块面板没有实现完整独立悬浮——原因已确认。**

相关代码：

- [assets/shell.css](../assets/shell.css)，约 99 行：`.aio > .chat-header` 为 `position: relative`、`height: auto`，仍参与正常布局。
- 同文件约 351 行：右上窗口控件展开时，`.panel-header__action` 获得 `margin-top: 36px`。
- [tests/native-transitions.cjs](../tests/native-transitions.cjs)，约 231 行：只检查标题 Y 不变、材质存在、margin 为 36px，没有检查标题父容器高度和消息视口是否移动。

本轮用现有代码及原有匿名 fixture 做只读机制验证：

| 指标 | 收起 | 右上展开 |
| --- | ---: | ---: |
| 标题栏高度 | 48px | 84px |
| 消息区域顶部 | 64px | 100px |
| 标题文字顶部 | 12px | 12px |

标题文字不动，但消息区下移了 36px。原测试仍会判为通过。这是测试标准的缺陷，不是已经解决。

修改方向：把标题、会话工具、窗口控件的定位和布局职责分开；消息视口在悬浮面板后保持完整，不通过撑高标题栏让位。滚动内容内设置必要安全留白，保证第一条和最后一条消息可达。保留原生按钮及 Electron drag/no-drag 命中，空白覆盖层不截获鼠标。

验收要检查展开前、中、后的消息视口边界、滚动位置、面板位置和点击命中，而非只检查标题位置。

**2. 输入框悬浮有时失效——症状确认，具体触发路径待定位。**

相关代码：

- [renderer/composer.js](../renderer/composer.js)，约 24、45、152 行：按可见性选择输入区，找不到时执行 `clean()`，删除浮动、宿主、区域和滚动标记。
- 同文件约 164–206 行：向上搜索消息区及共同祖先，用这些节点确定悬浮宿主。
- [assets/composer.css](../assets/composer.css)，约 2–21 行：仅在标记宿主、消息区域覆盖原生 `--inputAreaHeight`，浮动样式依赖 `data-liuli-composer="float"`。
- [tests/native-transitions.cjs](../tests/native-transitions.cjs)，约 80 行：模拟的原生预留高度恰好写在主题已覆盖的节点上。

风险包括：短暂不可见／零尺寸时撤掉仍有效的布局；缓存会话或节点复用时选错宿主；实际内层滚动／裁切祖先仍保留原生输入占位。尚不能断言本次故障是哪一种。

修改方向：确认实际视口、内容列表、裁切祖先、原生预留高度节点；对每个会话宿主维护明确状态，区分暂时不可测量与真正移除，在新宿主有效后再切换。恢复靠生命周期事件和有限重试，不增加常驻轮询。保留编辑器原节点和 IME 状态。

验收覆盖点击待输入、中文合成、多行、删除、撤销、图片／文件插入移除、消息滚动、会话切换及独立聊天。需要验证内容实际经过面板后方，不能以输入框是 absolute 或两个外框重叠作为通过条件。

**3. 输入时出现额外横线——人为绘制机制已确认。**

相关代码：

- [renderer/composer.js](../renderer/composer.js)，约 239、316 行：输入／删除时在光标旁添加 `.liuli-edit-feedback` 并动画淡出。
- [assets/composer.css](../assets/composer.css)，约 356 行：普通标记为 2×14px，删除标记为 12×2px 横线。
- 只读实验触发删除事件，确认生成了该横线及动画。

修改方向：移除光标旁额外绘制的标记。用户要求输入动画，并不等于要求添加横线。反馈应限于面板装饰或附件出现／移除等状态，不干预文字、光标、选区和中文合成。

注意：录屏也存在输入法原生合成下划线，不能把它一起删除。

**4. 左侧展开仍有贯穿长竖线——画面确认，绘制节点待定位。**

相关代码：

- [assets/shell.css](../assets/shell.css)，约 393 行已隐藏自建触发层伪元素，约 426 行隐藏已知 resize-handler 绘制。
- [assets/foundation.css](../assets/foundation.css)，约 127 行的结构清理覆盖 `.sidebar-nav/.sidebar-wrapper`；其他模块还使用原生 `.sidebar__nav/.sidebar__menu` 变体。
- 这些规则的存在不证明已经命中录屏中的实际分隔线。

修改方向：在真实线条位置确认绘制节点、伪元素、边框或内阴影，准确移除该装饰；保留原生拖拽命中和已要求的呼出方式。不要继续扩大到“所有边框透明”。

本轮录屏中的会话置顶小短线已可见，应与这条长分隔线分开验收。

**5. 搜索建议有额外空白外框——两种内容高度均可见，直接来源待确认。**

单行综合搜索入口与完整最近搜索列表，右侧都出现内容之外的空壳／宽条。

相关代码：

- [renderer/surfaces.js](../renderer/surfaces.js)，约 56 行 `clear()` 清空样式但未完全撤销此前的 surface 标记。
- 同文件约 79 行 `owner()` 通过通用父类及尺寸选择绘制拥有者；非零尺寸不能保证该节点是可见面板而非定位壳。
- 约 190 行先清外层、再给搜索内容加材质，内部清理仅覆盖已知结构。
- [assets/surfaces.css](../assets/surfaces.css)，约 90 行强制搜索内容宽度为侧栏宽度减 16px，外壳可以仍保持原生另一套宽度；约 124 行伪元素清理也并非完整撤销。

这些是具体代码风险，不是已经证明的实机唯一原因。

修改方向：区分原生定位壳、唯一玻璃表面和滚动内容；按真实组件统一宽度约束与内容高度；定位空壳不绘制。保留原生搜索开关、数据与定位；不要为了消除重叠隐藏整片会话列表。

验收包括单行入口、最近搜索、结果、无结果、加载、滚动和关闭，中间态也必须只有一套面板边缘。

**6. 群资料卡仍是旧样式——实际外观失败确认，注入／匹配断点待定位。**

必须区分三种结构：标题触发的小群资料卡、右侧群详情抽屉、独立资料窗口。录屏中的小卡仍为白底与原生蓝按钮；抽屉外层部分生效，内部字段仍有另一套底框。

相关代码：

- [load.js](../load.js)，约 18、115、215 行：有 URL 和宿主限制，执行脚本成功不等于实际可见卡片已命中样式；没有证据证明该卡片所在框架必然已注入。
- [renderer/surfaces.js](../renderer/surfaces.js)，约 6 行为资料类名列表，约 209 行独立路由回退直接取 `#app` 第一个非边框子节点。
- [作者 main 的 assets/layout.css:1535](https://github.com/LilycleHeart/qqnt-liuli-theme/blob/3d183f34184f58b7d2d935179c54505d5544ffc8/assets/layout.css#L1535) 明确排除空 `.mini-buddy` 占位层，并说明实际内容可能在 `.fake-target-element` 中。当前重构没有完整保留该例外。

作者例外遗漏可以确认，但不能因此认定录屏群卡片必然采用相同 DOM。

修改方向：按“真实窗口／框架和路由 → 主题版本与注入状态 → 可见节点及计算样式”逐层定位，再为具体组件建立适配。保留作者已有例外，明确一处玻璃拥有者；普通字段轻量化。不能继续靠猜测类名或按钮文案识别弹窗，也不能取消受保护窗口限制。

**7. 下载后的文件夹按钮错位——新增截图已确认，直接原因待定位。**

文件卡片在左侧，完成态文件夹按钮却靠近消息行最右边，明显脱离对应卡片。它属于消息附件操作区，不是输入工具面板中的文件按钮。

相关线索：

- [assets/bubbles.css](../assets/bubbles.css)，约 355 行统一 flex 排版；约 700、733 行重写消息行网格，包含可伸缩的 `minmax(0,1fr)` 内容列。
- 完成态操作按钮若仍使用原生整行网格或其他定位祖先，可能被推到远端；需要实际 DOM、grid-area、offsetParent 和坐标确认。
- 这些网格规则也存在于作者基线中，不能仅凭它们认定问题由本轮新增或证明直接原因。
- 现有测试没有覆盖真实文件下载状态转换后的按钮与卡片相对位置。

修改方向：针对文件消息建立卡片与原生操作按钮的局部布局关系，保留原生打开目录行为；不要用固定负 margin 或窗口宽度偏移硬拉回来。

验收覆盖未下载、下载中、完成、失败，以及历史记录直接加载完成态；接收／自己发送、长文件名、多文件、窗口缩放和系统缩放均应正常。图标与点击区域必须一致。

**为什么此前检查通过，实机仍失败**

1. 把圆角、blur、absolute 等样式存在当成目标完成，没有验证真实视口、裁切和点击区域。
2. 匿名 fixture 中的类名、窗口、输入预留高度是人为搭建的，不能替代实际 QQ 53644 结构；顶部测试甚至把错误的 36px 外边距作为成功条件。
3. 定位外壳、独立窗口、资料内容、消息特殊类型被通用猜测规则合并处理，作者原生例外没有完整继承。
4. 拆分 JS/CSS 文件并没有自动消除旧覆盖关系；消息样式仍含多轮对同一容器的覆盖。
5. 先前对修复完成的表述过早。提交、ZIP 一致性、模拟测试通过都不等于实际 QQ UI 验收通过。

后续应先修正验收标准，再运行：

- 顶部展开不改变整片消息视口的几何位置。
