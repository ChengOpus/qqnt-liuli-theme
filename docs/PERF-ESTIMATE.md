# 预估报告：Rust 重写与 QQ 内存（2026-11-15，未改代码）

依据：用户诊断包 `diagnostics-2026-11-15T01-15-56-702Z`（进程内存、主题启动耗时）、本仓库体积、此前的性能测量（`docs/UI-REWORK.md`）。所有数字来自这一份诊断和本机测量，没有在别的机器上复现。

## 1. 用 Rust 重写这个主题，能快多少

**结论：不建议，预计打开速度几乎不会变快，可能更慢。**

这个项目是什么：

| 部分 | 大小 | 跑在哪里 |
| --- | --- | --- |
| 样式（22 个 CSS） | 约 195 KB | QQ 每个窗口的 Chromium 渲染进程 |
| 脚本（约 30 个模块） | 约 550 KB 源码 | 同上，和 QQ 自己的页面在同一个 JS 引擎里 |
| 主进程部分（`load.js` 等） | 约 30 KB | QQ 主进程，由 SnowLora 执行 |

为什么 Rust 帮不上：

- 主题做的事几乎全是「改 QQ 的网页」：写样式、读写 DOM、听页面变化。这些只能通过浏览器提供的 JS 接口完成。Rust 要进渲染进程只能编译成 WebAssembly，而 WebAssembly 不能直接碰 DOM，每一次读写都要再经过一层 JS 胶水，还多了加载和实例化 wasm 的时间。
- 真正花时间的是浏览器自己（C++）做的样式计算、排版和绘制，不是主题的 JS 运算。比如此前测量的快速滑动：主题部分主线程约 1590 ms，其中样式计算约 290 ms、排版约 250 ms，脚本约 310 ms。这里的脚本时间大多也是 DOM 调用本身，换语言省不掉。
- 主题在主窗口的启动耗时，诊断里是 **173 ms**（从开始注入到就绪），QQ 自己的启动是秒级。即使把主题的纯计算部分全部换成 Rust、并假设零开销，能省下的也只是 173 ms 里很小的一块，**估计 0–10 ms**，用户感觉不到。
- 主进程部分（`load.js`）只做窗口登记、注入和几件小事，不在打开路径的瓶颈上；如果 SnowLora 本身是原生实现，那一层也不归本项目管。

真正能让打开更快的做法（都不需要换语言），按收益估计：

1. **按窗口类型拆分脚本**：现在每个窗口都执行全部约 550 KB 脚本。图片查看器、资料卡、小弹窗只需要样式和少数几个模块。预计每次打开这些小窗口省 **30–80 ms**，主窗口不变。
2. **样式按窗口拆分**：主窗口的输入框、会话列表、消息气泡规则在小窗口里用不上。预计小窗口的首次样式计算省 **10–30 ms**。
3. **让 Chromium 缓存编译结果**：现在脚本是作为字符串注入的，每次都重新编译。改为从文件 URL 以脚本标签加载，可以用上 V8 的代码缓存。预计每个窗口省 **10–30 ms**，需要确认 SnowLora 和 QQ 允许这样加载。

合起来，小窗口打开时间预计能减少几十到一百毫秒左右，主窗口变化不大。

## 2. 能不能降低 QQ 客户端的内存

诊断里这次 QQ 一共 9 个进程，合计工作集约 **1.44 GB**：

| 进程 | 工作集 | 私有内存 |
| --- | ---: | ---: |
| 主进程（Browser） | 332 MB | 125 MB |
| GPU 进程 | 168 MB | 108 MB |
| 渲染进程 ×5（主窗口、设置、聊天池窗口等） | 321 / 183 / 168 / 154 / 51 MB | 236 / 126 / 105 / 97 / 14 MB |
| 网络、音频服务 | 37 / 22 MB | 7 / 1 MB |

### 主题自己占的部分（估算）

- 每个被主题化的窗口：解析后的样式约 3–6 MB，脚本和它的数据约 5–10 MB，图片壁纸解码后的位图约 4 MB（1280×720），壁纸的 base64 字符串在 localStorage 和样式表里各存一份（几百 KB）。合计**每个窗口约 12–20 MB**。
- 视频壁纸（主窗口和打开的设置页各一份）：解码器和帧缓冲，加上 1885×1323 的画布（约 10 MB），以及 GPU 侧的纹理。估计**每个播放视频的窗口 40–80 MB**。

### 能做什么，预计省多少

| 做法 | 预计节省 | 代价 |
| --- | ---: | --- |
| 视频壁纸画布按 1 倍像素比绘制、最长边不超过 1600 | 每个窗口约 6–8 MB | 高分屏上壁纸略软（本来就在磨砂玻璃后面） |
| 窗口最小化或隐藏超过 30 秒后完全释放视频解码器，回来时重新加载 | 每个窗口 30–60 MB（最小化期间） | 恢复时首帧图先出现，约 0.3 秒后视频接上 |
| QQ 预先建好、藏起来的池化窗口，在真正显示之前不注入主题 | 每个这样的窗口约 12–20 MB | 第一次显示时多一次注入，配合 .18 的预置样式不会闪 |
| 壁纸不再以 base64 字符串在每个窗口里各存一份，改由宿主提供文件地址 | 每个窗口不到 1 MB | 改动壁纸存储格式，需要迁移旧设置 |

合计：**主题相关的内存大约能降 30–100 MB**（有视频壁纸时偏高）。占 QQ 总量（约 1.4 GB）的 2%–7%。

### QQ 自己的内存

剩下的 1.3 GB 以上是 QQ 本身：Chromium 的多进程、QQ 预先创建的隐藏窗口、消息缓存、各模块的原生代码。主题能碰到的手段都不理想：

- **Chromium 启动参数**（例如限制 JS 堆、关闭某些功能）必须在 QQ 启动之前设置。SnowLora 注入的时候进程已经起来，来不及；要改只能改 QQ 的启动方式，这超出了「不修改 QQ.exe 和加载器」的约定。
- **强制回收工作集**（Windows 的 EmptyWorkingSet）只会让任务管理器里的数字暂时变小，内存页随后会被换回来，还会增加卡顿。不建议。
- **关闭 QQ 预建的隐藏窗口**会影响 QQ 打开聊天窗口和通知的速度，也可能引起功能问题。不建议。

所以对 QQ 本身的内存，本项目能做的基本只有「不额外增加」。

## 建议的下一步（如果要做）

1. 视频壁纸的画布降分辨率，最小化或隐藏后释放解码器。收益最大，改动最小。
2. 池化窗口延后注入。
3. 按窗口类型拆分脚本和样式。
